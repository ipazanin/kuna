# Module map

Kuna is a modular monolith. It is one Vite build, one PWA and one deploy, and inside it each app is a module with its own folder, its own record kinds and its own file. A module owns its records and its rules, publishes a small contract that is not its internal model, and imports only what this map allows. One write touches one file, so a save is all or nothing.

The reasons for this shape, and the patterns it was weighed against, are in the [hub design](hub.md).

## Inside a module

An app is cut by business feature, such as `bankLoans`, `holdings` or `rules`, and each feature holds `domain`, `application`, `infrastructure` and `presentation` folders. Dependencies point inward.

- Domain code imports only its own app's domain code and the domain parts of the kernel in `DOMAIN_SHARED`: `src/shared/storage/domain/`, `src/shared/calendar/`, `src/shared/money/`, `src/shared/text/`, the category swatches and the `domain` folders of `categorising`, `mail`, `recipes` and `privacy` (`tests/importBoundaries.spec.ts`, `keeps domain code to its own app's domain code, the record types, the rules core and the calendar, money and text helpers`).
- Application code imports no infrastructure, except the files in `ADAPTER_WIRING` (`keeps application code off infrastructure, but for the files that wire the adapters`).
- Storage adapters live in `src/shared/storage` and each app's `workbook/infrastructure`, and only storage code, an app's `app.ts`, the fake and real-books seeds and a pack's tab mappings import them (`keeps the storage adapters inside the kernel's storage and the app's workbook, which its app.ts wires in and a pack maps its tabs with`).
- Each kind an app stores has a name of its own, and a pack's kinds start with the pack's name (`tests/kindNames.spec.ts`, `names each kind once, so the document holds one list of it and its codec is the one found` and `starts each pack kind with the pack's name, while core's kinds stay bare`).
- An app's `assistant` folder is what the chat gets from it, kept out of the business features. The files directly in it are chat code: the `AppAssistant` with its places, settings and guides, the reader over the app's own store and the words. They read the store only through what `app.ts` hands in and import no write. `assistant/operations/` holds the operations, which plan each step through the write functions the screens use, and is the only part that writes. Chat code never imports it statically, and `app.ts` loads it with the assistant. The hr-doo pack has its own `assistant` folder with its kinds, reports, build-ups and operations, which Company's `app.ts` passes to the company's assistant. `assistant/infrastructure/fake/` holds the replies the fake build's chat gives for that app, which `app.ts` loads only in the fake build. The pack's `assistant/infrastructure/fake/` holds its own, such as a travel order's costs, which Company's `app.ts` loads beside Company's. Kuna's own settings for the chat are in `src/shell/assistant/`, with their fake chat in its `infrastructure/fake/`.

## Published contracts

A contract is the types a module gives others, kept apart from the types it computes with. A change to the internal model then breaks one translation file, not the reader's screens.

### What an app gives the shell

`AppContribution` (`src/shared/app/appContribution.ts`) lists an app's id, name, colour, screens, menu, Settings, home card, hub part, set-up lines, first run, suggested set-up order, sync group, what it tells the chat, lets it read and lets it propose (`assistant`, a lazy `AppAssistant` built in `src/apps/<app>/assistant/`, with the reader contract in `src/shared/app/assistantReader.ts` and the operations contract in `src/shared/app/assistantOperations.ts`), the exchange rates its records need (`ratesDemand`), which the shell hands to `src/shared/rates`, and what it starts while the page is open. The shell never sees an app's records. Net worth reads each app's hub part as labelled figures with a caption and a link (`HubPart`, `CountedHubPart` and `AppHub`). An app that counts adds its parts into the personal sum, and one that does not, the company, shows its parts beside it. `personalNet` adds them up (`src/shared/app/personalNet.ts`, called from `src/shell/netWorth/NetWorthScreen.vue`), and `homeCardFigures` turns an app's store state into figures, a wait or a failure (`src/shared/app/homeCardFigures.ts`). It also holds what its data is for the delete dialogs (`AppData`, `src/shared/storage/application/appData.ts`).

Each hub part carries a `key`, an English phrase that names it in both languages and never by a name a person gave, such as a loan by its lender and payout day. `netWorthSides` (`src/shared/app/netWorthSides.ts`) splits the parts into what you have and what you owe, which `personalNet` takes one from the other, Net worth draws as two rings (`src/shell/netWorth/netWorthRings.ts`) and the chat reads as Kuna's `net_worth` report (`src/shell/assistant/kunaReader.ts`).

An app's home card may also give one button through `useAction`, which the card calls once in its setup and which returns the button's label, icon, busy state and run, or null to hide it. Investments gives Fetch today there.

Each app builds its hub part from its own model in its own file: `companyHubFigures` (`src/apps/company/home/presentation/companyHubFigures.ts`), `loansHubFigures` (`src/apps/loans/home/presentation/loansHubFigures.ts`) and `investmentsHubFigures` (`src/apps/investments/home/presentation/investmentsHubFigures.ts`).

### What the pack gives the company app

`PackContribution` is the company app's only way into the pack. Core code never imports pack code. It calls the slots, such as `ownerTakeOut` (`src/apps/company/packs/packContribution.ts`), which the company's hub part reads through `shownPack` (`src/apps/company/home/presentation/companyHubFigures.ts`). Without the pack, `NO_PACK` answers every slot with nothing (`src/apps/company/packs/packContribution.ts`). The writes reach the pack the same way: an import asks `repaymentsOf` what its new rows pay back of the costs the owner paid and has `linkRepayments` link them, and the move to the items tab lets `linkToItems` split what the pack's records count today.

### What one app publishes to another

An app may publish facts in one file, `src/apps/<app>/facts.ts`, with types of its own. A reading app imports it from one translation file and nowhere else. The first use is Loans' published bank loans for Assets. Loans keeps `BankLoan` with its principal, dates, instalments, interim interest, subsidy and repayment type (`src/apps/loans/workbook/domain/bankLoan.ts`). It publishes `PublishedBankLoan`, which holds only a key, a name, what is owed on the day and a link. Assets reads it in `src/apps/assets/loans/application/assetLoans.ts`. Each published record carries the link a row names it by (`PublishedLinkTarget` in `src/shared/app/rowLinks.ts`), so Spending never spells Loans' app id or kinds. A `facts.ts` may also publish a command, which writes through the app's own store and gives back what the reader needs: Loans' `addMovement` adds a movement to an informal loan and gives its link and an Undo. Spending runs it from its one translation file, `src/apps/spending/links/application/loanTargets.ts`, and `src/apps/spending/links/application/linkWithRecord.ts` then links the row, so Loans writes first and one Undo takes back both. Assets reads the same `facts.ts` for bank loans and runs no command. Company publishes its OIB as `PublishedCompany`, apart from its settings, and Spending reads it in `src/apps/spending/company/application/companyFacts.ts` to tell a receipt bought for the company. The company's other facts for the personal apps, such as the owner loan, would follow the same rule.

What a published bank loan owes is your part of it. A bank loan or an asset you hold with others keeps your part from the start on its own record and dated changes of it in its own kind, `loan-share` in Loans and `asset-share` in Assets, and both read your part on a day through `partOnDay` in `src/shared/money/yourPart.ts`. Assets takes the part Loans publishes off its own part of the asset's value, and Net worth counts only your parts.

Facts that a matching across apps reads go to the shell instead, through a slot on `AppContribution` whose type sits in `src/shared/app`, since the shell imports no app. Spending's `facts.ts` builds the rows it has linked to records in other apps (`PublishedRowLink` in `src/shared/app/rowLinks.ts`), its `app.ts` hands them over as `rowLinks`, and `linkedRows` in `src/shell/routing/appRegistry.ts` gathers them by app. The shell hands each app a `ShellReads` (`src/shared/app/appContribution.ts`) as it installs, whose `linkedRows` reads them afresh at each call. Loans keeps it from its `app.ts` and reads the rows linked to its instalments in `src/apps/loans/bankLoans/application/statementPayments.ts`, so a bank loan's plan shows each instalment as paid, late or not seen in your statement.

Company hands the shell its bank rows to and from the owner the same way, as `moneyWithOwner`, typed by `PublishedOwnerPayment` in `src/shared/app/moneyWithOwner.ts`. Company builds them in `src/apps/company/transactions/application/publishedMoneyWithOwner.ts` from the pack's `moneyWithOwner`, names each by its row id, and asks the pack's `paysForTrip` which tax-free pay is a travel allowance, so no other app reads ruleset keys. `ShellReads.moneyWithOwner` gives them by app, and Spending keeps the read in `src/apps/spending/links/application/companyTargets.ts`, which `linkTargets.ts` lists beside Loans' records, so a row links to a payment as it links to a loan's instalment.

Company hands over the costs the owner paid privately in the same slot, as `PublishedOwnerAdvance` beside the payments, so the slot carries the money between a company and its owner rather than only its bank rows. Each advance is linked by its id in the pack's kind, which the pack names through `ownerAdvanceRecords`. Spending's entry dialog starts a new one with `addOwnerAdvance`, a command in `src/apps/company/facts.ts` that writes through Company's store and the pack's `addOwnerAdvance` slot. Spending runs it, and reads the categories an advance may take from `advanceCategories`, only from `src/apps/spending/company/application/companyFacts.ts`. `src/apps/spending/links/application/linkWithRecord.ts` then files the row under For the company, linked to the advance, so Company writes first and one Undo takes back both, as it does for Loans.

Company reads which of its ledger rows and costs the owner paid other apps link to through `ShellReads.linkedRows` in `src/apps/company/transactions/application/spendingSightings.ts`, and Transactions marks each as seen in Spending. Loans and Company read every app's links whose target names them, through `linksNaming` in `src/shared/app/rowLinks.ts`, so neither spells the id of the app that links.

Loans hands the shell the records a row may link to the same way, as `loanTargets`, typed by `PublishedLoanTargets` in `src/shared/app/loanTargets.ts`: each bank loan's instalments and extra payments, and each informal loan with its movements. Loans builds them once per read of its books in `src/apps/loans/facts.ts`. `ShellReads.loanTargets` gives them by app, and Spending keeps the read in `src/apps/spending/links/application/loanRecords.ts`. `src/apps/spending/links/application/linkTargets.ts` gathers every app's targets under the app's id, so a link reads against the targets of the app it names and the picker lists every app's, each with its own wait or failure.

Investments hands the shell its deposits and withdrawals the same way, as `cashMovements`, typed by `PublishedCashMovement` in `src/shared/app/cashMovements.ts`, each with its account's name and its euros at its own rate. Fees and fee refunds stay out, since no bank row pays them. Investments builds them once per read of its books in `src/apps/investments/transactions/application/publishedCashMovements.ts`. `ShellReads.cashMovements` gives them by app, and Spending keeps the read in `src/apps/spending/links/application/investmentTargets.ts`, which `linkTargets.ts` lists beside the others, so a row links to a broker deposit as it links to a loan's instalment and To review offers the deposit a row may pay.

Assets hands the shell its assets the same way, as `assets`, typed by `PublishedAsset` in `src/shared/app/assetTargets.ts`, each with its name, what it is and the day it was bought. Assets builds them once per read of its books in `src/apps/assets/asset/application/publishedAssets.ts`. `ShellReads.assets` gives them by app, and Spending keeps the read in `src/apps/spending/links/application/assetTargets.ts`, which `linkTargets.ts` lists beside the others. Spending publishes each linked item with its euros at its row's rate and how it counts, so Assets reads back from `ShellReads.linkedRows` in `src/apps/assets/rows/application/linkedRows.ts` what the rows linked to an asset paid and earned, and writes nothing into Spending.

## What may import what

### When a capability moves into `src/shared`

A capability gets one owner in `src/shared` when two modules use it and both change it for the same reason. With one user, it stays in that app. Two copies that change for different reasons stay two copies.

- **Moves.** The find-or-pick resume that Loans and Investments repeat (`src/apps/loans/app.ts`) changes whenever the shared find-or-pick flow changes, so Assets' plan moves it to `src/shared/storage/presentation/resumeFileLookup.ts` before a third copy appears.
- **Stays.** The DZS house price index has one user, Assets. Investments fetches prices by GET from vendors with quotas, while the DZS takes a POST and answers JSON-stat on a statistics office's release cycle. The two change for different reasons.
- **Stays apart.** Performance's periods and the shared chart ranges look alike, but they change for different reasons, so Performance's domain does not import `src/shared/charts`.
- **No shared ledger.** Company and spending share only the fields the rules read. A shared transaction type would pull owner share and the balance chain into spending, or strip them from the company.

A shared module's contract is its exported types and functions, and none of them takes an app's books. Each app builds the input from its own model and keeps that builder, as `categorisationContextOf` does for the company (`src/apps/company/rules/domain/categorisationContext.ts`).

## Extractions for spending and AI assist

What the company app and Investments held and spending and AI assist would change for the same reason has moved, up to spending's statements stage. The duplicate-row key has no module of its own: `occurrenceKeys` sits beside `factKey` in `src/shared/text/factKey.ts`, and the camt and profile readers stay in Company, since neither OTP nor Revolut gives camt and the profile reader cannot read Revolut.

Each move is a relocation plus import paths, lands in its own commit with `npm run check`, the boundary spec and `check:figures` identical before and after, and only then does spending import it. The order:

1. The ECB rule and fetch, and the category swatches, before spending v1.
2. Spending v1, which imports none of the moved company code.
3. `foldRuleText` into `src/shared/text`, beside `fold` (`src/shared/text/fold.ts`), then the rules core.
4. Mail filing made generic, then moved.
5. The duplicate-row key, into `src/shared/text`.
6. Spending's statements stage.
7. The secrets file, as the first stage of the AI assist plan.
8. Spending's receipts stage.

## How the boundary spec will state it

None of these is a new kind of rule.

1. Add `spending` and `assets` to the apps the first test checks (`reads the imports it checks` in `tests/importBoundaries.spec.ts`), and their stores to `ADAPTER_WIRING`.
2. `DOMAIN_SHARED` holds `src/shared/categorising/domain/`, `src/shared/mail/domain/`, `src/shared/recipes/domain/` and `src/shared/privacy/domain/`, so an app's domain code may import them. A shared module's adapters go in `infrastructure` folders, which domain code still may not import. App domain code reads rates only as the `RateBook` of `src/shared/money`, so `src/shared/rates` is not in the list.
3. Keep "no app imports another" with one table of exceptions: each published `facts.ts` and the one file of another app that may import it, starting with `src/apps/loans/facts.ts` read by `src/apps/assets/loans/application/assetLoans.ts`. A new case checks that every listed reader exists and imports the file, and that `facts.ts` imports nothing outside its app and `src/shared`.
4. A shared capability module imports no other capability module except through its domain, so `categorising`, `mail` and `rates` do not grow into one. Moving `foldRuleText` to `src/shared/text` removes the only edge between them.

`tests/kindNames.spec.ts` extends to the new apps' kinds.
