## Findings first

1. **Today's parity holds.** Every camt file in the archive reads as one statement. The app's reader and the Apps Script's `parseCamtStatement` agree on every head and on every cell of every entry, verdict included (0 differences). The dry run against the export gives no new rows and refuses none, with every entry already on the ledger. The entries match their ledger rows in every ingest column. The few verdicts that differ from the ledger are all rows `flagged_by = owner`, so hand corrections. `parity:rules` over the full ledger (working tree): 0 differences, the verdict equal to the ledger's category on most rows, the client-rule synthetic case also clean.
2. **The fetch needs two pieces of `ErsteCamt.gs` and one of `Categorise.gs`.** `saveCamtStatement` names each XML from `camtDocumentHead` (Code.gs:425), which uses `camtNamespace`, `camtStatementElements`, `camtChild`, `camtText`, `statementLabel` (ErsteCamt.gs:28-35, 100-130, 184-191) and `normaliseIban` (Categorise.gs:81-83). Staging those two files whole would break the fetch's XML naming. A 40-line head reader moves into `Code.gs`. The draft does this, and on the real archive it files the same file names the archive holds today, then skips all of them on a second run.
3. **The kept ledger formatting would delete any column the app adds to the ledger.** `formatLedgerTab` ends with `trimColumns(sheet, header.length)` (Code.gs:230), and `trimColumns` deletes every column past the 18 the schema names (Code.gs:350-355). `requireLedgerTabShape` reads only the first 18 header cells (Code.gs:147-152), so it does not stop on a 19th. Wave 13b adds `owner_share` to the ledger. The first 06:00 run after that column appears would delete it and its values. The formatting must become header-driven and lose `trimColumns` in the Wave 13 push, before 13b. The draft does this.
4. **The morning refresh is a second writer of the `accounts` tab.** `refreshWorkbook` calls `seedHumanTabs`, which appends an account the ledger names but the tab lacks (Data.gs:99-147). The app now owns that tab (Settings, Accounts). The plan keeps "the fetch and the ledger formatting" only, so the seeding goes with the rest. Nothing else in the morning writes a cell value.
5. **About 25 places in the app exist only to mirror the Apps Script.** The big ones: `parity:rules`, the whole-tab rules check (`rulesTabRefusals.ts`), the rule order-tie report and refusal, `hasClientsTab`, the "keep at least one IBAN" guard, and the reasons given for ledger placement and blank-row rules. They are listed under _What goes or simplifies in the app_. Ledger placement itself is a decision for the owner (see _Open questions_).
6. **Order matters.** `parity:rules` loads every `.gs` file in the scripts folder (scripts/parity-rules.mjs:55-56), so it breaks the moment the four files leave it. The app's rules guards must stay until the morning ingest is gone, or a rule the app saves could stop the ingest. So: proof, the owner's review, the app's sync deployed, the Apps Script push, then the app commit that removes the mirrors and `parity:rules`.

### What the kept files look like

The draft is in the scratch folder (`kept/Code.gs`, `kept/Data.gs`). Against today's files:

**`Code.gs`**

- Menu: _Fetch Erste statements from Gmail_, _Format the ledger_, _Install daily triggers_. _Ingest camt statements_, _Refresh ledger and green tabs_, _Preview camt ingest_ and _Back-test categorisation_ go.
- `dailyPass`: `installDailyTriggers()`, `fetchErsteStatements()`, `formatLedger()`. No try and rethrow is left, since the step it protected is gone. A failed fetch throws, so the trigger's failure mail goes out, and the formatting waits a day.
- `fetchErsteStatements` reads its folder from the `statements_folder` settings key (a path from My Drive, default value `work/company/business-bank-account/erste/statements`). It walks the path with `getFoldersByName` and stops with a message when a segment is missing, instead of `childFolder`, which creates it (Code.gs:518-521). Year folders are still created as today. Google's Folder reference says `getFoldersByName` "Gets a collection of all folders that are children of the current folder and have the given name" and `createFolder` "Creates a folder in the current folder with the given name" (https://developers.google.com/apps-script/reference/drive/folder, loaded 2026-10-23).
- File naming is unchanged: PDF `<delivery date>-statement-<NNN>.pdf`, XML `<label>-<account>.xml`, label-only for an IBAN the accounts tab lacks. Lane 2's sync skips files by this name, so it is now a contract between the fetch and the app.
- `camtDocumentHead`, `camtChild`, `camtText`, `normaliseIban` move in. The head reader takes the first `Stmt` and checks only that `CreDtTm` and `LglSeqNb` are there.
- `formatLedgerTab` is header-driven: the header is row 1 up to its last filled cell, `date` and `category` must be there, the text format goes on the seven signal columns by name, the number formats on `date`, `amount` and `balance` by name, widths by name. No `trimColumns`, no `ensureColumns`, no schema and no throw on a header it does not know. Banding, the filter (kept when it covers the table), the category colour rules and the tab colour stay as today.
- Gone: `LEDGER_SIGNAL_COLUMNS`, `LEDGER_TAB_COLUMNS`, `ERSTE_STATEMENTS_PATH`, `CATEGORY_FAMILIES`, `OWNER`, `FINANCING`, `refreshWorkbook`, `requireLedgerTabShape`, `setLedgerSignalColumnsToText`, `round2`, `ensureRows`, `ensureColumns`, `trimColumns`, `folderByPath`, `archivedCamtIdentity`, `backtestCategorisation`, `ledgerRecords`, `ledgerRowSignals`, `storedSignal`.

**`Data.gs`**

- Keeps `CATEGORIES_TAB` (the colour rules read the tab), `ACCOUNTS_TAB`, `SETTINGS_TAB`, `ACCOUNT_HEADERS`, `SETTINGS_HEADERS`, `accountColumns`, `accountNameByIban`, `settingRow`, `settingColumns`.
- Gone: `HUMAN_TAB_COLOR`, `CLIENTS_TAB`, `CATEGORY_HEADERS`, `CLIENT_HEADERS`, `CARD_SETTLEMENT_IBANS_KEY`, `BUCKET_VOCABULARY`, `seedHumanTabs`, `seedCategoriesTab`, `restrictColumnToVocabulary`, `seedBucketOf`, `seedAccountsTab`, `appendUnknownAccounts`, `requireAccountIbans`, `inferAccountIbans`, `requireCardSettlementIbans`, `requireClientIbans`, `writeHumanTab`.

Smoke run of the draft (`smoke-kept.mjs`): with the key set, the first `dailyPass` files every file the real archive holds, under the same names, from two deliveries of every XML, and a second fetch saves 0. The formatting made 0 calls to `deleteColumns`, `insertColumnsAfter` or `setValues`. Without the key, the fetch stops with the settings message and nothing is filed. The fakes do not prove the Sheets calls behave as on Google, so the first real run stays the decisive check (see push steps).

### What the Apps Script still needs of the Sheet

The fetch reads the `accounts` tab by its `account` and `iban` headers and stops on an IBAN named twice (Data.gs:154-214). It reads `settings` by its `key` and `value` headers. The formatting reads the ledger's `date` and `category` headers and the `categories` tab's `category` and `colour` columns, and colours only `#rrggbb` values (Code.gs:299-303). So these app guards stay, with new reasons: the accounts and settings headers, one IBAN per account across the tab. Everything else the app guards "for the Apps Script" can go.

## Apps Script changes and push steps

For the planning session. **Stop for the owner's review before step 3.** Each step's check is in Executions (Extensions, Apps Script, Executions), the decisive place for this project.

1. **App side first.** The app's sync is deployed and has filed at least one real statement, or the proof's check 10 passed. The app knows the `statements_folder` key (so Settings shows it and does not report it as unknown).
2. **Settings row.** The owner adds `statements_folder` = `work/company/business-bank-account/erste/statements` through the app's Settings. Check on a fresh export that the row reads back.
3. **The script change** (after the owner's yes), in the Drive's `work/company/company-finance/shadow-accounting/scripts/`:
   - Replace `Code.gs` and `Data.gs` with the reviewed versions of the drafts.
   - Move `CamtIngest.gs`, `ErsteCamt.gs`, `Categorise.gs` and `Rules.gs` with plain `mv` to the Drive's `_to-delete/work/company/company-finance/shadow-accounting/scripts/`, and add one line to `_to-delete/README.md`.
   - Check that the folder holds only `.clasp.json`, `appsscript.json`, `Code.gs`, `Data.gs` (and Drive's `Icon` file, which clasp does not push).
4. **Push.** `npx @google/clasp push -f` from `scripts/`. clasp's README says push "always replaces the whole content of the online project with the files being pushed", so the four files leave the online project too, and `-f` "Forcibly overwrites the remote manifest" (https://github.com/google/clasp, loaded 2026-10-23). Reload the Sheet so `onOpen` rebuilds the menu.
5. **First run by hand, never by the trigger** (memory note: "Never let the 06:00 trigger be the first run of anything that writes rows or deletes tabs"). Run _Format the ledger_ from the menu: the ledger keeps all 18 columns, banding and filter cover the data, category colours show, no value changed. Then _Fetch Erste statements from Gmail_: the dialog says saved 0 (or the new statements) and already present for the rest. Then `dailyPass` from the editor's function list: green in Executions.
6. **App commit**, the same day: the removals under _What goes or simplifies in the app_, `parity:rules` gone, README and the handoff's check list updated. Deployed green.
7. **Next morning.** The 06:00 `dailyPass` green in Executions, no ledger row added by the script, and the next statement filed by the app on its first sync with the balance continuing.
8. **Records.** A `work/log.md` entry (the push, the files staged, the first runs), the shadow-accounting hub sections above, the memory note, and a "Done" line under Wave 13 in plan.md.

Rollback, if step 5 or 7 fails: move the four files back from `_to-delete/`, restore `Code.gs` and `Data.gs` from the Drive's version history or the staged copies, push again. The ledger is untouched by the change, so nothing in the Sheet needs restoring.

## Open questions

1. **Ledger placement.** With the Apps Script gone, new ledger rows go newest first only for a person reading the Sheet. Keep it until the JSON storage move removes the Sheet (no work now), or append at the foot (about 50 lines and their specs go, and the Sheet's rows stop reading newest first). I recommend keeping it, since the JSON move is next and deletes it anyway.
2. **Seeding.** The plan names only the fetch and the formatting. Dropping the seeding stops the script appending accounts to a tab the app owns. Confirm that nothing should be seeded any more.
3. **A missing `statements_folder` row.** The draft stops the fetch, as the hub's rule for script-read keys says. The other choice is a default in the script equal to the app's default, which keeps working if the row is deleted but puts the default in two places.
4. **Undo for rules.** Rules keep no Undo today (README, _Write-back_). Once rules are ordinary records and can be deleted, should a delete and a change carry Undo like other tabs?
5. **Category colour storage in Wave 12c.** The kept formatting colours only `#rrggbb` values. If 12c stores a swatch name instead of a hex, the Sheet's category colours stop. Either 12c keeps hex in the cell or the formatting learns the swatch names.
6. **After the JSON move.** The fetch still reads `accounts` and `settings` from the bound Sheet to name files and find its folder. When the Sheet becomes a read-only archive, the fetch needs both from somewhere else (the JSON file, or a script property and file names without the account). The JSON storage research should carry this.
7. **A label-only file after its account is added.** The fetch names an unknown IBAN's statement by label alone, and the hub tells the owner to rename it by hand. With Wave 13 the app parses such files anyway and dedups by reference, so a second copy under the full name is clutter, not a double count. Keep the hand rename in the hub, or drop it.
