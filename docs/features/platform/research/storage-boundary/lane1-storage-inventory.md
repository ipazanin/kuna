## 1. Write call sites outside the workbook feature

### How every write runs

`writeThrough` (`workbookStore.ts:338-377`) picks the adapter (`:354`), reads the tabs fresh (`:355`), plans on that read (`:356`), writes (`:361`), reads back (`:362`), keeps the read-back copy (`:363`), verifies (`:364`) and records the session write (`:366`). So every call site below re-reads before it writes. What differs is how the plan finds the row again:

- Row writes (`planRowsChange`, `tabRowWrites.ts:109`) find each changed or deleted row on its own row number if that row still holds every rule column as read, else on the one row that does, and refuse on none or several (`locate`, `tabRowWrites.ts:296-306`, `holds` at `:312-318`). Added rows are not matched, except that a ledger import refuses an (account, reference) already on the tab (`imports/application/ledgerRows.ts:57-67`).
- Ledger verdicts (`planVerdicts`, `writePlans.ts:28`) match by `LedgerRowKey`: (account, reference), or (account, date, amount, balance, description) for a blank reference (`ledgerRowKey.ts:31-44`, `writePlans.ts:242-253`). They also refuse when category or `flagged_by` changed since the read (`writePlans.ts:51-57`).
- Rules (`planRulesChange`, `writePlans.ts:99`) match by rule id (`:116`) and check the expected cells (`rules/domain/rulesTabChange.ts:33-60`).
- Settings (`planSettingsChange`, `writePlans.ts:162`) match by key (`:175`) and check the expected value (`:190`).

Undo: `canUndo` allows it for `ledger` and `rows` writes and never for rules or settings (`workbookStore.ts:92-94`). Row writes made through `useRowWrites` get an Undo toast (`workbook/presentation/useRowWrites.ts:72`). Ledger writes through `useLedgerWrites` get one too (`review/application/useLedgerWrites.ts:63`). Every `ledger` and `rows` write also carries Undo in Review's "Changes in this session" (`review/presentation/SessionChanges.vue:137-146`, wired at `ReviewScreen.vue:295` to `store.undo` at `:120`).

## 4. The read side

**Getting rows.** Google: `readSnapshotFrom` (`workbook/infrastructure/googleWorkbookPorts.ts:21-45`) asks for the tab ids, then one `batchGet` of the tabs the Sheet has, with `UNFORMATTED_VALUE` and `SERIAL_NUMBER` dates (`sheetsClient.ts:27-28`). xlsx: `readWorkbookFile` (`workbookFile.ts:35`). Both go through `sheetRowsFromValues` (`workbookSnapshot.ts:78-94`), which keys cells by trimmed header, numbers rows from 2 and drops blank rows. The browser copy is the same `SheetRow[]` per tab in IndexedDB (`workbookCache.ts:22-66`). `readWorkbook` turns the snapshot into the domain `Workbook` on every show (`workbookStore.ts:227-233`, `workbookReader.ts:32-72`).

**Where header names live.** `TEMPLATE_COLUMNS` holds every tab's columns with notes (`workbookTemplate.ts:48`). The rules columns come from the rules domain (`rules/domain/rule.ts:54`). `BILLING_PLAN_COLUMNS` repeats five of them (`billingPlanTabReader.ts:7`). The readers then name each column again as a literal, about 147 times (`cells.category`, `optionalDate(cells, 'due')` and so on). The tests repeat the ledger header (`tests/fixtures/writeBack.ts:16-35`). Writes check against `WRITABLE_COLUMNS` (`workbookWriter.ts:113-130`) and `LEDGER_VERDICT_COLUMNS` (`:102`).

**Who reads which tab.** In infrastructure: `workbookReader.ts` reads categories (`:132`), accounts (`:173`), clients (`:243`), invoices (`:292`), owner-advances (`:350`) and ledger (`:393`). 8 tab reader files read assets, outgoing-plan, dismissed, grants, plan, scenarios, splits and year-end. In domains: settings (`settings/domain/settings.ts`, `parseSettings`) and rules (`rules/domain/readRules.ts`) already parse in the domain, but over cell-shaped rows that carry `sheetRow` (`readRules.ts:7-10`). So 14 of the 16 tabs are parsed in infrastructure.

**What `cellReading.ts` does.** Cell conversion: `dateOf` takes a serial number to a `CivilDate` (`:61-63`), `moneyOf` a number to `Money` (`:65-67`), plus `textOf`, `slugOf`, `booleanOf` and `wholeNumberOf`. Row helpers that throw a reason: `requiredDate`, `optionalPeriod`, `positiveMoney`, `requiredYear`, `requiredChoice` (`:88-137`). `TabReading` pairs facts with problems by `sheetRow` (`:10-19`).

**Where business parsing is mixed with cell mapping.** Every tab reader does both in one function. Examples: grants need both parts or neither, and the parts must add up to the amount (`grantsTabReader.ts:43-79`). A category is defined by its first row in tab order with category, family and a known bucket (`workbookReader.ts:126-140`). A client IBAN two clients claim is refused (`workbookReader.ts:243-263`). ## 5. The adapters, the port and what a third adapter needs

**The port** (`workbook/application/workbookWriter.ts:77-82`) has two methods. `read(tabs)` returns `FreshTabs`, which per tab is the header row, `SheetRow[]` and `lastRow` (`:7-15`). `write(edits, before)` takes `TabEdits` (`:68-74`): `CellEdit` names a tab, a `sheetRow` and a header (`:38-43`), `RowAppend` gives cells by header and an optional `at` row (`:46-50`), `RowDeletion` a `sheetRow` (`:53-56`), and `NewTab` a header (`:59-62`). The order of operations is part of the contract, since `planRowsChange` computes every row's final number assuming deletions first, then placed rows from the top, then restored rows, then appends at the foot (`tabRowWrites.ts:139-168`).

**Google adapter** (`workbook/infrastructure/googleWorkbookWriter.ts:22-92`). It reads the tab ids and the tabs, then turns `TabEdits` into one `batchUpdate`: `addSheet` and header, `updateCells` per cell, `deleteDimension` bottom up, `insertDimension` with `copyPaste` of format and validation for placed rows, `appendCells` at the foot, and `repeatCell` date or text formats from `cellFormats.ts`. It refuses a write planned before a read (`:34-36`) and a column the app never writes (`:225-237`).

**Browser adapter** (`workbook/infrastructure/localWorkbookWriter.ts:15-66`). It works on a copy of the snapshot's tabs. The header is the template's columns plus any other column the rows use (`:72-76`), since the stored rows keep no header. It replays the Google row shifts by hand (`:37-63`). The store saves the copy only after the read-back (`workbookStore.ts:363`).

**Snapshot and store.** `WorkbookSnapshot` is meta plus `SheetRow[]` per tab (`workbookSnapshot.ts:36-53`). The meta mixes both sources: `ledgerSheetId` and `missingTabs` are Google facts, `lastExportedAt` and `unexportedSince` are Excel facts. `WorkbookStorePorts` (`workbookStore.ts:142-163`) is Google-shaped: `fetchFromGoogle`, `prepareSync`, `hasLiveAccessToken`, `forgetGoogleSignIn`, `signOutOfGoogle`, `googleWriter`.

**What a third adapter (IndexedDB records or a server API) must implement today.**

1. `read` that returns tabs as header-keyed `SheetRow`s with 1-based row numbers, a header list and `lastRow`, with cells typed as Sheets returns them unformatted: dates as serial numbers, amounts as numbers, checkboxes as booleans. Every reader depends on this (`cellReading.ts:61-67`).
2. `write` that reproduces a spreadsheet's row arithmetic exactly: deleted rows close up, placed rows push rows down, appended rows land after `lastRow`. Otherwise `verifyRowsChange` (`tabRowWrites.ts:218-244`) fails, and Undo puts rows back on the wrong numbers.
3. Atomic all-or-nothing writes, as `batchUpdate` gives (README "Write-back").
4. Row order as business meaning. The ledger's `sequence`, statement placement (`ledgerRows.ts:125-152`, mirroring the Apps Script's `insertPositionFor`) and "first row defines a category" all assume a stable tab order.

**Places outside the adapters it would force a change in.**

- The adapter switch is two-way on `meta.source` (`workbookStore.ts:354`). `refreshAfterFailedWrite` is Google-only (`:370-372`, `:380-390`), and so is `withTabsReadBack` (`:322-330`). `sync` only reads Google (`:420-425`). `replaceLocalWorkbook` makes an Excel-mode copy only (`:439-448`).
- `WorkbookSource` is `'google' | 'excel'` (`workbook/domain/workbook.ts:43`), and so is `WorkbookChoice` (`workbookChoice.ts:4`). 16 files outside workbook branch on the two names (`grep -rlE "=== 'google'|=== 'excel'|!== 'excel'|!== 'google'" src`), mostly copy ("the Sheet" or "this browser"), `missingTabs` checks and Sheet links.
- `WorkbookStorePorts` is Google-specific in 6 of its 12 members (`workbookStore.ts:142-163`).
- The cache keys rows by `sheetRow` (`workbookCache.ts:24`).
- The 41 call sites in section 1 build cells and row numbers themselves, and the 70 files in section 2 hold `sheetRow`.
- The fake build's inline `import.meta.env.VITE_FAKE_WORKBOOK` guards sit in the composition (`workbookStore.ts:516,523,541`, `main.ts:16`), and `scripts/assert-no-fake-bytes.mjs` proves they fold away. Any new wiring must keep them inline.

## Open questions for the plan

1. Should tab order stay a business fact? The ledger's `sequence` decides closing balances, statement placement mirrors the Apps Script, and "first row defines a category" follows Sheets. A record store without order would need an explicit ordering field. Keeping order means every adapter must keep the spreadsheet's row arithmetic.
2. Should the opaque reference show in the UI? "Row N" appears in 29 files' messages and in the Sheet link on Review. An opaque reference either loses those, or the adapter supplies a display label such as "row 57 of the Sheet".
3. Do rules stay cell-shaped? The rules domain mirrors `Rules.gs` cell by cell, and `parity-rules.mjs` needs raw cells per transaction. Moving rules to business terms is a separate decision.
4. Who owns `OWNER_ADVANCE_ROWS` and the asset, grant and year-end row rules? They live in the workbook feature and in `settings/application/workbookTabRows.ts` but serve the hr-doo pack. Moving them is a change in what owns what, so it needs the owner's answer.
5. Does the import-boundary check need a new dev dependency? There is no lint tool today. A small Node script or a Vitest test over the import graph needs no install. ESLint or dependency-cruiser would.
6. Should Drive, Picker and Gmail access, which invoicing reuses from `workbook/infrastructure`, move to a shared Google boundary?
