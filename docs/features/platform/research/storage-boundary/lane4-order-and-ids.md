## 1. The ledger's same-day order

**Today.** `Transaction.sequence` is the ledger tab's position turned around (`workbookReader.ts:395-399`, documented at `workbook/domain/workbook.ts:62-67`). Eleven consumers sort by `date, sequence`, among them the closing balance (`cash/domain/balances.ts:101-104`), receivables payments (`receivables/domain/invoiceMatching.ts:192-194`), owner loans (`packs/hr-doo/domain/ownerLoans.ts:171,188`), corporate tax payments (`cit/matchCitPayments.ts:53-55`), the asset register (`assets/assetRegister.ts:160`), reimbursements (`reimbursements.ts:29`), accrual bookings (`accrual/accrualBookings.ts:186`), the import checks (`imports/application/ledgerRows.ts:46-53`) and the Transactions list (`transactions/domain/listedRows.ts:87-94`).

**The new rule.** Within one account and day, each entry's balance is the previous balance plus its amount. The chain gives the order. The first entry opens at the previous day's closing balance, which breaks a tie the chain alone leaves. The reference breaks any tie left after that. Across accounts on one day no field decides, so entries go by account name.

**On the export** (`ledger-order.mjs`): every ledger row reads with no problem. On every account-day with two or more entries the chain allows exactly one order, and it equals today's `sequence`, with or without the opening balance anchored on the previous day. No day is ambiguous, so the reference never decides, and every day's first entry opens at the previous day's closing balance.

So the chain reproduces today's order on every account-day.

**Across accounts** (`ledger-order-figures.mjs`): a few days have entries on both accounts. Ordering those by account name changes the cross-account order on some of them. Every figure stays the same: latest balances, monthly balance series, receivables, owner loans, reimbursements, asset register, owner advances, forecast for each year, Waiting for you, and the Transactions list order. Accrual differs only in the order of its `bookings` list for the two years (`accrual-diff.mjs`: "same items, order differs"). Its lines, adjustments, bridge, tax base, liability and category totals are unchanged, and so are the year-end comparison and open items (`yearend-diff.mjs`).

**When the chain fails.** A hand-typed balance can break the chain. The parser then orders that day by reference and reports one problem for the account and day, saying the closing balance is a guess. Today such a day silently follows tab order. There is no such day on the export.

## 3. Ids for the seven kinds without a business key

**The seven kinds and their tabs:**

| Tab              | Kind               |
| ---------------- | ------------------ |
| `splits`         | split parts        |
| `plan`           | plan lines         |
| `year-end`       | year-end lines     |
| `owner-advances` | owner advances     |
| `outgoing-plan`  | billing plan items |
| `dismissed`      | dismissals         |
| `assets`         | assets             |

`plan`, `scenarios` and `dismissed` are missing from the export. When the app adds one, the template's columns go in, so it starts with the `id` column.

**Four of the seven already have a key the reader enforces.** Assets by name (`assetsTabReader.ts:21-24`), year-end lines by year, statement and line (`yearEndTabReader.ts:44-48`), dismissals by kind and key (`dismissedTabReader.ts:16-17`), and plan lines other than purchases (`planTabReader.ts:7-12,27-33`). Only split parts, owner advances, billing plan items and plan purchases have none. See the plan's open questions.

**The format.** A version 4 UUID from `crypto.randomUUID()`. MDN's page (loaded 2026-10-22, https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID) says it returns "a randomly generated, 36 character long v4 UUID", is "available only in secure contexts (HTTPS)", is available in Web Workers and is "Baseline Widely available ... since March 2022". The page itself did not render its table. MDN's compat data (`api/Crypto.json` in `mdn/browser-compat-data`, fetched with curl) gives Firefox 95, Chrome 92 and Safari 15.4. The app already calls it (`workbookStore.ts:532`, `googleAuth.ts:56`, `invoiceMessage.ts:31`), so Firefox needs nothing new. The app runs on GitHub Pages over HTTPS and on localhost in development, both secure contexts. The id column goes last on each tab, written as text.

**The Apps Script reads none of the seven tabs.** It opens `ledger` (`Code.gs:176`), `categories`, `accounts`, `settings` and `clients` (`Data.gs:13-16`, used at `:39,107,189,292,344`) and `rules` (`Rules.gs:9,184,355`), all by name. `getSheetByName` is its only way in. It has no `getSheets` call, and its one `insertSheet` (`Data.gs:373`) seeds categories and accounts. `Data.gs:11` names `outgoing-plan` in a comment about tab colour only. The script files are `CamtIngest.gs`, `Categorise.gs`, `Code.gs`, `Data.gs`, `ErsteCamt.gs` and `Rules.gs` in the shadow-accounting `scripts/` folder on the owner's Drive.

**How the live Sheet gets ids.** The app finds rows without an id and shows a notice, worded like the add-tab consent today (`FactTabCard.vue:44`, `SplitDialog.vue:85`): "N rows on M tabs have no id yet. Add them?" Accepting writes, in one write, an `id` header after each tab's last column and a new id on every row that lacks one. The count the owner sees comes from the owner's live Sheet. The notice stays in the app afterwards, so a row added by hand, or by an app tab that was open before the deploy, gets its id the same way.

Two things the adapter must handle. `addSheet` makes a 26-column grid (`googleWorkbookWriter.ts:59`, Sheets' default), but a tab the owner made or trimmed by hand may have no free column. The Google adapter reads each tab's column count with the tab ids and adds a column first when needed. A copied row carries its id, so two rows share one. Both are refused as a duplicate, and the problem says to clear the copy's id cell, after which the notice gives it a new one.

**The ledger is keyed mostly by content.** Most ledger rows have a blank reference (`ledger-keys.mjs`), so `LedgerRowKey` falls back to account, date, amount, balance and description (`workbook/domain/ledgerRowKey.ts:30-44`) for most of them. That key has 0 collisions on the export.
