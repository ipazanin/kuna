# Wave 12b lane 3: sources and mechanics for the storage boundary

Read-only research on HEAD 7128551, 2026-10-22. Every source below was downloaded with curl into a scratch folder and searched as plain text, so each quote is checked against the page, not a search snippet. One source could not be loaded and is marked unconfirmed.

## Recommendation in short

Keep one storage port and make it speak in records. Features hand the store a typed list of record changes ("add client", "set the verdict on ledger record R", "delete plan line R"), each with the record as the app read it. One adapter call applies the whole list in one batch or refuses it. Each adapter owns the record-to-column mapping. Do not build a repository per record type and do not build a separate Unit of Work object.

The reason in plain words: the app already reads the whole workbook into memory at sync, so the half of Repository that matters most (query access) is already done by the snapshot. What is left is the write half, and that is a Unit of Work: a list of changes committed as one batch with a conflict check. The app has that shape today in `TabRowsChange`. A repository per record type would add about a dozen interfaces with two implementations each, plus a Unit of Work to put them back into one batch, to get what one typed change list gives.

The cost of the recommendation: one discriminated union of record changes (about 16 kinds, see the counts below), a mapping per kind in each of the two adapters, and moving the readers and the column lists out of the features. The mapping work exists either way. The repository option costs that plus the interfaces and the unit of work.

### The passages that matter

**Repository (Fowler).** "Mediates between the domain and data mapping layers using a collection-like interface for accessing domain objects." The motivation is queries: "it can be worthwhile to build another layer of abstraction over the mapping layer where query construction code is concentrated. This becomes more important when there are a large number of domain classes or heavy querying." And: "Client objects construct query specifications declaratively and submit them to Repository for satisfaction."

**Repositories (Evans, DDD Reference p. 17).** "For each type of aggregate that needs global access, create a service that can provide the illusion of an in-memory collection of all objects of that aggregate's root type." Then: "Provide repositories only for aggregate roots that actually need direct access."

**Aggregates (Evans, p. 16).** "Use the same aggregate boundaries to govern transactions and distribution. Within an aggregate boundary, apply consistency rules synchronously."

**Entities (Evans, p. 11).** "This means of identification may come from the outside, or it may be an arbitrary identifier created by and for the system, but it must correspond to the identity distinctions in the model. The model must define what it means to be the same thing."

**Unit of Work (Fowler).** "Maintains a list of objects affected by a business transaction and coordinates the writing out of changes and the resolution of concurrency problems." And: "A Unit of Work keeps track of everything you do during a business transaction that can affect the database. When you're done, it figures out everything that needs to be done to alter the database as a result of your work." The motive it names is call count: changing the database with each change "can lead to lots of very small database calls, which ends up being very slow."

**Data Mapper (Fowler).** "A layer of mappers that moves data between objects and a database while keeping them independent of each other and the mapper itself." And: "With Data Mapper the in-memory objects needn't know even that there's a database present."

**Identity Field (Fowler).** "Saves a database ID field in an object to maintain identity between an in-memory object and a database row." And: "in order to write data back you need to tie the database to the in-memory object system."

**Optimistic Offline Lock (Fowler).** "Prevents conflicts between concurrent business transactions by detecting a conflict and rolling back the transaction." The condition that matters here: "So long as the validation and the updates occur within a single system transaction the business transaction will display consistency."

**Identity Map (Fowler).** "Ensures that each object gets loaded only once by keeping every loaded object in a map."

**Hexagonal Architecture (Cockburn, 2005).** Intent: "Allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases." On what a port is: "The protocol for a port is given by the purpose of the conversation between the two devices." On how many: "At the one extreme, every use case could be given its own port, producing hundreds of ports for many applications. [...] Neither extreme appears optimal." and "My selection tends to favor a small number, two, three or four ports". His hospital example has "one for the prescription database", one port for a whole database. On the test side: "we create an interface to a repository, a RepositoryFactory that will produce either the mock database or the real service object, and the in-memory mock for the database."

**ContractTest (Fowler bliki, 2011, retitled 2018).** This is about checking a test double against the real external service, not about one suite over several implementations: "These check that all the calls against your test doubles return the same results as a call to the external service would." And: "These tests need not be run as part of your regular deployment pipeline."

**Contract Tests (Rainsberger, 2017).** This is the one-suite-many-implementations sense: "It's quite common, in fact, to start with a concrete test for the production implementation of the collaborator, and then extract a Contract Test by extracting a factory function for creating the subject of the test." And the rule for what to test: "If Client A stubs B.foo() to return value X, then write a Contract Test for B that shows when to expect(foo()).toEqual(X)." On initial state: "Whoever implements Model has to provide a way to initialize a Model instance that can't find/doesn't have entity."

**Sheets batchUpdate (Google).** "Changes are grouped in a batch so that if one request is unsuccessful, none of the other (potentially dependent) changes are written."

**Sheets developer metadata (Google).** "For example, if developer metadata is associated with row 5 and another row is then subsequently inserted above row 5, that original metadata is still associated with the row it was first associated with (what is now row 6)." And: "If the associated object is deleted then its metadata is deleted too."

## 2. What each source means for this app

The app is a client-side SPA with no server. A sync reads every tab into a `WorkbookSnapshot` of `SheetRow`s keyed by header (src/features/workbook/infrastructure/workbookSnapshot.ts:7-10, 78-94), and `readWorkbook` turns it into the domain `Workbook` the screens query in memory. A write goes through `writeThrough` (src/features/workbook/application/workbookStore.ts:338-377): pick the adapter (:354), read the touched tabs fresh (:355), plan on that read, write (:361), read back (:362), keep the read-back copy and verify. The port is `WorkbookWriter { read, write }` (src/features/workbook/application/workbookWriter.ts:77-82), and its write takes `TabEdits` of cells, appends and deletions addressed by tab, header and `sheetRow` (:37-74). Four store entry points feed it: `setVerdicts`, `changeRules`, `changeSettings` and `changeRows` (workbookStore.ts:392, 397, and the methods around 468-487). So the brief's "one write path through store.changeRows" is close but not exact: there is one write funnel, `writeThrough`, with four planners in front of it.

**Repository.** Its main job, per Fowler, is to concentrate query construction when there is "heavy querying". This app has no queries against storage. It reads the whole workbook once per sync and every screen filters arrays in memory. The snapshot plus `readWorkbook` already plays "the illusion of an in-memory collection" for every record type at once. What a repository would add here is only the add and remove half. Evans also ties repositories to aggregate roots "that actually need direct access", and the app has not named its aggregates. Introducing repositories would force that naming (does a split belong to its ledger record, does a plan line belong to its plan year), which is an ownership decision the owner reserved.

**Unit of Work when the storage call is already one batch.** Fowler's Unit of Work has two jobs: track what changed, and write it out in one go while resolving concurrency. The single `spreadsheets.batchUpdate` covers only "write it out in one go". The tracking job is done today by the caller, who builds the change list explicitly: `TabRowsChange` with `added`, `changed`, `removed` and `restored` (src/features/workbook/domain/rowChanges.ts:24-30) is literally "a list of objects affected by a business transaction". Fowler's classic UoW registers objects as they are touched, which fits mutable objects. Here the domain records are `readonly` interfaces, so an explicit change list is the natural form. Conclusion: the change list is the unit of work and the port's apply call is its commit. A separate `UnitOfWork` class is needed only when several repositories must contribute to one batch, which is a cost of the repository option, not a need of the app. Today every write touches exactly one tab: verdicts write `ledger` (src/features/workbook/application/writePlans.ts:63-66), rules write `rules` (:122-126), settings write `settings` (:185-195), and `planRowsChange` plans one `rules.tab` (src/features/workbook/application/tabRowWrites.ts:109-111). A record-changes list keeps the door open for a write across two record types without new machinery.

**Concurrency is Optimistic Offline Lock, with a gap.** The re-read, find-again and refuse-on-change logic (`locate` at tabRowWrites.ts:296-306, `holds` at :312-318) is Optimistic Offline Lock with the record as read standing in for a version number. Fowler's condition is that validation and update run "within a single system transaction". Sheets has no conditional write, so the re-read and the batchUpdate are two calls with a window between them in which the morning ingest or a person can change the Sheet. The read-back check after the write (`verifyRowsChange`, tabRowWrites.ts:218-244) detects a bad outcome but cannot roll it back. The port contract should state this honestly: an adapter applies the list whole or not at all, and it refuses when a record no longer matches what was read at the time it checks. A future adapter on a real database could close the window, and the contract would not change.

**Data Mapper.** This is the pattern the wave asks for: "the in-memory objects needn't know even that there's a database present". Today the mapping sits in the features. For example `invoiceCellsOf` turns an invoice into header-keyed cells and serial dates (src/features/receivables/application/invoiceRows.ts:29-41), and `INVOICE_ROWS` names the columns and calls the infrastructure reader (:9-10, 43-57). Nine files outside the workbook feature define or take such `TabRowRules` (command: `grep -rln "TabRowRules" src --include='*.ts' --include='*.vue' | grep -v "^src/features/workbook/"`). Moving those mappings into each adapter is the Data Mapper move.

**Identity Field, and the row number that shifts.** Fowler's Identity Field stores the store's key in the object. A spreadsheet's only built-in key is the row number, and it shifts when the ingest inserts statements above a row or a write deletes one. Evans says the model must define "what it means to be the same thing". The app already has a domain rule for the ledger: same account and reference, or for a blank reference the same booking (src/features/workbook/domain/ledgerRowKey.ts:30-44). For the other tabs `holds` matches on every column the app writes, with case ignored on some (tabRowWrites.ts:312-318), and refuses when none or several rows match (:296-306). So identity in this app has two parts: where the record stood when read (a hint, tried first, :298) and what it held (the real check). That maps to two things the domain needs: an opaque reference for "which record" and the record as read for "is it still the same". The second already travels in each change as `before` (rowChanges.ts:13-17).

**Sheets developer metadata as a stable row id: considered, not recommended.** Google says metadata on a row stays with it when rows are inserted above. It would give each row a stable id on the Google side. Against it: rows the Apps Script ingest or a person adds would carry none, an xlsx export would drop it, the browser workbook has nothing like it, and each write would add requests. Whether metadata survives a sort or a cut-and-paste in the Sheet UI is unverified (the pages loaded do not say). The current match-by-content already handles inserted rows.

**Identity Map.** Not needed. The snapshot holds each record once per sync, and records are immutable, so there is no "two watches" problem inside a session.

**Ports and adapters.** Cockburn favours few ports, each named by the purpose of the conversation, and his examples use one port per database. Storage is one conversation ("keep the books"), so one port. The Google Sheet and the browser workbook are two adapters on it, and the Google fake is a third used by tests and the fake build.

## 3. The main choice

**Option A: one record-changes port.** The application hands the store `readonly RecordChange[]`, a discriminated union by record kind and action, for example `{ kind: 'client', action: 'add', client }`, `{ kind: 'ledger', action: 'setVerdict', ref, before, after }`, `{ kind: 'planLine', action: 'delete', ref, before }`. The port is two calls: read the records of some kinds fresh, and apply a list of changes. Each adapter maps each kind to its tab and columns and returns a receipt in record terms. Undo stays what it is today, the inverse list (`undoOfRows`, rowChanges.ts:40-47) applied through the same call. The guards that refuse a change (today `TabRowRules.refusals`, tabRowWrites.ts:44-45) work on records before and after, so they can live in the domain per kind.

- For the user: nothing visible changes. Every write is still one batch, refused whole or applied whole, and Undo works as now.
- Cost: one union type of about 16 kinds (the 16 writable tabs, workbookWriter.ts:18-35, of which `settings` and `rules` have their own planners today), one mapping per kind in each of two adapters, one contract suite. The planner in `tabRowWrites.ts` (338 lines, `wc -l`) stays generic and moves behind the port.
- Risk: the union can rot into an untyped bag (`{ kind, fields: Record<string, unknown> }`). Keep each kind's record type exact.

**Option B: a repository per record type, with a unit of work.** `ClientRepository.add/update/remove`, `LedgerRepository.setVerdict`, and so on, each implemented for Google and for the browser workbook, plus a `UnitOfWork` that collects their changes into one batchUpdate.

- For the user: the same as A.
- Cost: about 16 repository interfaces times 2 adapters, a unit of work to merge their changes into one batch (needed because Sheets wants one batchUpdate per write and the app relies on all-or-nothing), and either 16 contract suites or one suite that knows every repository. The read side of each repository would duplicate what the snapshot already gives.
- Benefit: call sites read as domain verbs (`clients.add(client)`), and each repository's surface is small and obvious. In a server app with SQL and heavy querying this would be the usual choice, and Evans and Fowler both describe it for that setting.

**Recommendation: A.** The app reads everything at sync, writes small batches, and needs every write atomic in one storage call. Those three facts remove the reasons Repository exists (queries) and make Unit of Work the heart of the write side. Option A is a Unit of Work handed to one port, which is what the code already does in tab terms. The wave changes the vocabulary from tabs and cells to records and moves the mapping into the adapters. If the owner later wants domain verbs at call sites, a feature can add a function that builds the change (`addClientChange(client)`) only where it states a real rule, without a repository layer.

## 4. The opaque record reference

**What needs it.** `sheetRow` appears 411 times in 70 files outside `src/features/workbook/` (commands: `grep -ro "sheetRow" src --include='*.ts' --include='*.vue' | grep -v "^src/features/workbook/" | wc -l` and the same with `-rl`). The plan's figure of 68 files was taken before the last commits. It does five jobs today:

1. Which row to change: `CellEdit.sheetRow`, `RowDeletion.sheetRow` (workbookWriter.ts:40, 55), and every draft and guard in the settings domain, such as `TabRowDraft.sheetRow: number | null` (src/features/settings/domain/tabRowDrafts.ts:29).
2. Order as a tie-break, which is a domain meaning: the invoice comment says the row "is also the order the invoices were written in" (src/features/workbook/domain/workbook.ts:117-118). Examples: src/features/receivables/domain/invoiceMatching.ts:124, 171, src/features/billingPlan/domain/plannedAgainstInvoiced.ts:71-72, src/features/billingPlan/domain/fillRestOfYear.ts:44, src/features/settings/domain/tabRowDrafts.ts:40, src/features/rules/domain/readRules.ts:41.
3. Equality and lookup: sets and maps of touched rows (tabRowWrites.ts:70, 114).
4. Problem messages that name a row (`WorkbookProblem.sheetRow`, workbook.ts:186).
5. The "open in Sheet" link: `sheetRowLink` (src/features/workbook/infrastructure/sheetRowLink.ts:5-10), called once from src/features/review/presentation/ReviewScreen.vue:80.

**How to model it: a branded string.** The repo already brands primitives this way: `CivilDate = string & { readonly __calendar: 'day' }` (src/shared/calendar/civilDate.ts:5) and `Money = number & { readonly __unit: 'cents' }` (src/shared/money/money.ts:5). TypeScript's own playground documents the convention ("an intersectional type, with a unique constraint in the form of a property called __brand (this is convention) which makes it impossible to assign a normal string"), and the compiler's own `type Path = string & { __pathBrand: any }` (node_modules/typescript/lib/typescript.d.ts:3670-3672) uses it. So: `type RecordRef = string & { readonly __record: 'ref' }`.

Why not the alternatives:

- A class with `#private` fields: the domain records sit in Vue reactive state and drafts, and MDN says a Proxy "does not have direct access to the original object's private elements", which throws `TypeError: Cannot read private member`. Vue's `reactive` and deep `ref` are Proxies. Equality would also be by object identity, so two reads of the same record would not be `===`.
- A class with TypeScript `private` (not `#`): the handbook says a class with a private member is only compatible with instances "from the same class", so it is nominal at compile time and proxy-safe. It still loses `===`, needs an `equals` method, and does not work as a `Map` key or a `v-for` key without converting to a string.
- An object `{ tab, row }`: the domain could read `row`, which is what the wave is removing.

A string compares with `===`, works as a `Map` and `Set` key and a `v-for` key, survives `structuredClone` into IndexedDB and Vue proxies, and costs nothing at runtime. Its weakness is that anyone can write `as RecordRef` or split it. The boundary check below can flag `as RecordRef` outside the workbook feature's infrastructure, and the format is documented as internal.

**What the Google adapter puts inside.** The tab and the row as read, for example `invoices:57`. Nothing else is needed, because the change already carries the record as read (`before`), and the adapter turns that into the cells to match with its own column mapping. That keeps today's behaviour exactly: try the row as read first, else the one row that holds the same cells, else refuse (tabRowWrites.ts:296-306). The browser workbook numbers its rows the same way (src/features/workbook/infrastructure/localWorkbookWriter.ts:39, 52, 57, 62), so it can use the same encoding. A future database adapter would put its primary key there.

**Equality.** `===` on the string, valid within one read. After a sync, a record that moved gets a new reference. This is fine because Undo and edits re-match by content, not by reference.

**Sorting without row numbers.** The readers deliver rows in tab order (`sheetRowsFromValues`, workbookSnapshot.ts:78-94). Since ES2019 `Array.prototype.sort` is stable (MDN: "Since version 10 (or ECMAScript 2019), the specification dictates that Array.prototype.sort is stable."), so a domain sort by date keeps tab order for ties, and the `|| a.sheetRow - b.sheetRow` tie-breaks can go when the input is in tab order. Where a function merges or filters lists from two places and needs tab order back (for example tabRowDrafts.ts:40), the reader can give each record a plain `position` number with no write meaning, or the feature keeps the reader's order. Which one is a per-call-site judgement for the implementation.

**"Open in Sheet" and row names in messages.** The domain never decodes the reference. The workbook feature exposes, from its application layer, one function that turns a record reference into a link (`null` for the browser workbook, which already has `ledgerSheetId: null`, workbookSnapshot.ts:43-44) and one that names the place for a person ("row 57 of invoices"). Both are real rules about the store, so they are not empty wrappers.

## 5. The import-boundary check

**What the repo has.** No ESLint and no dependency-cruiser in `package.json` (devDependencies list checked). `scripts/check-foreign-import.mjs` is **not** an import-boundary check. It drives the production build in a headless browser to import xlsx files another program wrote (scripts/check-foreign-import.mjs:1-9) and runs in CI as `npm run check:import` (package.json:23, .github/workflows/deploy.yml:40-41). A new boundary check must not reuse the `check:import` name. CI runs `npm run typecheck` and `npm test` on every push to main (deploy.yml:27-30). There is a precedent for a unit test that reads source files: tests/devOnlyMarkers.spec.ts:14.

**What the check must catch, measured on HEAD.** A scratch prototype (`boundary-probe.mjs` in the research session's scratch folder, run with `node`) found:

- 78 imports in 35 files outside `src/features/workbook/` that reach `src/features/workbook/infrastructure/` (matches `grep -rlE "from '[^']*workbook/infrastructure/" src ... | wc -l` = 35). Two of them are in `src/main.ts`, one a dynamic `import()` of the fake seed (src/main.ts:17). The composition root needs an allowance.
- 15 imports in 8 core files that reach `src/packs/`, including `src/shared/routing/router.ts` and `src/features/transactions/application/splitRows.ts`.
- 2 domain files that import an outer layer: src/features/imports/domain/profileGuess.ts and src/features/imports/domain/tabularStatement.ts.
- 20 dynamic `import()` calls in `src` (command: `grep -rnE "import\(['\"]" src --include='*.ts' --include='*.vue' | wc -l`).

**The options compared.**

|                       | Vitest spec or node script using TypeScript's scanner | ESLint `no-restricted-imports`                                                                                    | dependency-cruiser                           |
| --------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| New dependencies      | none (`typescript` and `vue` are already installed)   | `eslint`, `typescript-eslint`, `vue-eslint-parser`, and a flat config                                             | `dependency-cruiser`                         |
| Dynamic `import()`    | yes                                                   | no: "It applies to static imports only, not dynamic ones."                                                        | yes, with a `dynamic` attribute in rules     |
| `.vue` files          | yes, via `vue/compiler-sfc` `parse`                   | yes, with `vue-eslint-parser`                                                                                     | yes, via `@vue/compiler-sfc` per its FAQ     |
| How paths are matched | resolved file paths                                   | the import string as written, with gitignore-style or regex patterns, per-folder config blocks for relative paths | resolved file paths, `from`/`to` regex rules |
| CI wiring             | none if it is a test (`npm test` already runs)        | a lint step                                                                                                       | a step                                       |

The prototype uses `ts.preProcessFile(code, true, true)`, which on a sample returned type-only imports, a multi-line import, `export ... from`, a side-effect import and a dynamic `import()`, and skipped an import path inside a comment. Over `src` it read 423 `.ts` and `.vue` files and 3644 import specifiers. It needs about 30 lines: walk `src` with `readdirSync(root, { recursive: true })` (works on the local Node 24.21.0, and CI uses `lts/*`), take both `<script>` and `<script setup>` from `.vue` files, resolve relative specifiers, and test each against a short rule table.

**Recommendation: a Vitest spec, `tests/importBoundaries.spec.ts`.** It runs in `npm run check` locally and in the existing CI test step, adds no dependency and no CI step, and catches dynamic imports, which ESLint's rule cannot. A plain script in `scripts/` would do the same job but needs its own `package.json` script and its own CI step. dependency-cruiser is the right tool if the rule table grows past a handful of rules or the owner wants dependency graphs, at the cost of one dev dependency. The rule table at the start: nothing outside `src/features/workbook/` imports its `infrastructure/` (except `src/main.ts`), no `domain/` folder imports an `application/`, `infrastructure/` or `presentation/` folder, and nothing outside `src/packs/` imports `src/packs/` (the seam lane decides the exceptions, such as the router). Each failure names the importing file, the target and the rule.

## 6. The contract suite in Vitest

**Mechanics.** Two forms work and both have sources.

- `describe.each` with one row per adapter factory. Vitest documents `describe.each` and `describe.for`, the difference being that "`each` spreads array case" and "`for` doesn't spread array case". The repo already uses the `describe.each([[name, harness]])` form in 9 spec files (command: `grep -c "describe.each" tests/*.ts | grep -v ":0"`), for example tests/tabRowWrites.spec.ts:100-103 over `googleHarness` and `excelHarness`. Those 9 files hold 110 `it` calls between them (command: `grep -cE "^\s+it\("` per file), some of which run only against Google.
- A function that takes a factory and declares the tests, called from each adapter's spec file. This is Rainsberger's "extracting a factory function for creating the subject of the test" and Cockburn's RepositoryFactory.

With two adapters in one repo, the first form is plainer: one file, `tests/recordStoreContract.spec.ts`, with one `describe.each` row per adapter. The second form pays off only when an adapter lives elsewhere or a third adapter wants its own file.

**What the suite tests.** Rainsberger's rule: test every behaviour the store relies on. From the write funnel (workbookStore.ts:338-377) and the README's Write-back section, that is: records read back as written for each kind, including dates as dates and text that looks like a number staying text, added records land after the last one and the ledger's go where its order says, a change applies whole or not at all, a change to a record that moved on since the read is refused, a record is found again after rows were inserted above it, a delete closes the gap, and an inverse change (Undo) restores the store, including a deleted record on its old position.

**What each factory needs.** Each factory takes a seed in business records and returns the port plus a way to play an outside edit:

- **Google fake.** `createFakeSheets(grids, numberFormats)` (src/features/workbook/infrastructure/fake/fakeSheets.ts:22) builds a fresh Sheet per test. It applies a batchUpdate on copies and keeps them only when every request goes through (:60-63), and it handles all seven request kinds the writer sends (`addSheet`, `insertDimension`, `deleteDimension`, `updateCells`, `appendCells`, `repeatCell`, `copyPaste` at :79-110). The factory turns the seed into a header row and value rows with the Google adapter's own mapping, then wraps the fake in the Google adapter (today `googleWorkbookWriter(sheets)`, src/features/workbook/infrastructure/googleWorkbookWriter.ts:22). The outside edit mutates `sheets.grids`, which the interface documents for exactly this ("Tests change them to play the ingest or a person in the Sheet", fakeSheets.ts:13-14). It must not use `fakeSheetsSession()`, a module-level singleton for the fake build (:169-172).
- **Browser workbook.** `localWorkbookWriter(tabs)` (localWorkbookWriter.ts:15) copies the tabs into a private working copy (:16) and has no header row, using the template's columns plus any other column its rows use (:72-76). The factory builds `WorkbookTabs` from the seed with the browser adapter's mapping. Since the working copy is private and the store makes a new writer per write from the current snapshot (workbookStore.ts:354), an outside edit is played by changing the tabs and building the adapter again. Persistence to IndexedDB happens in the store, not in this adapter, so the contract suite needs no `fake-indexeddb`.

**Behaviours that stay out of the shared suite.** The browser workbook always holds every tab (README, Write-back: "In Excel mode the workbook always holds every tab, so nothing is added"), while the Google adapter leaves missing tabs out of a read (googleWorkbookWriter.ts:25-31) and can add one with consent. Formats, dropdown copying and request order are Google-only too. These stay in the Google adapter's own spec, as the request-level assertions in tests/fixtures/writeBack.ts (`sentRequests`, `writtenRanges`) do today.

**The other sense of contract test.** Fowler's ContractTest checks the fake against the real service on its own rhythm, outside the pipeline. For this app that is the README's manual test against a copy of the Sheet (README "Manual test, against a copy of the Sheet first"). It stays manual, since CI makes no Google calls.

## Corrections to the brief

- `scripts/check-foreign-import.mjs` is an end-to-end check of importing foreign xlsx files, not an import-boundary check. Its npm name `check:import` is taken.
- The write side has one funnel (`writeThrough`) with four planners (`setVerdicts`, `changeRules`, `changeSettings`, `changeRows`), not one path through `changeRows`.
- `sheetRow` is in 70 files outside the workbook feature at HEAD, not 68. The infrastructure imports are in 35 files, not about 20.

## Open questions for the owner

1. **Records without a natural key.** Splits, plan lines, year-end lines, owner advances, outgoing-plan lines, dismissals and assets are found again by all their written cells, and two identical rows make the write refuse. Keep that, or add an id column to those tabs? An id column changes the tab shape, the template and possibly the Apps Script, so it is your call. My recommendation is to keep matching by content, which works today.
2. **Tie-breaks on tab order.** Is "the order the invoices were written in" a business rule you want named in the domain (a `position` on the record), or is reader order plus stable sort enough? I lean to reader order, with a `position` only where a function merges lists.
3. **Domain verbs at call sites.** Is `store.apply([{ kind: 'client', action: 'add', client }])` readable enough for you, or do you want per-kind functions that build the change? These would be plain functions, not repositories.
